# plugin-attendance

Плагин посещаемости для звонков OpenVidu/LiveKit. Показывает текущих и вышедших участников, время входа и выхода, длительность присутствия и состояние подключения к событиям звонка.

Форма выгрузки отчёта находится внизу окна, под списком участников. Выберите `PDF` или `CSV (Excel)` и нажмите «Скачать». Отчёт содержит минималистичную таблицу: одна строка на участника, все периоды присутствия рядом и общая длительность в часах, минутах и секундах. В шапке указаны начало отслеживания, время формирования и часовой пояс браузера. Технические идентификаторы сеансов и состояния подписки в отчёт не выводятся. Выгрузка доступна и после удаления трекера из памяти: достаточно открыть страницу с тем же `callId`.

Backend — один Gradle-модуль на Java 25 и Spring Boot. React/TypeScript-интерфейс собирается вместе с backend и раздаётся из одного исполняемого JAR. Текущая версия плагина — `1.0.2`, зависимость Java SDK — `pluginsdk:plugin-sdk:1.1.0`.

## Архив посещаемости

В окне плагина откройте вкладку «Архив», введите логин, с которым вы участвовали в звонке, и нажмите «Показать» или Enter. Можно выбрать период по дате начала учёта. Изменять Meet для поиска архива не требуется.

После завершения звонка откройте [архив плагина](https://calls.vareonix.cc/apps/plugin-attendance/?view=archive), введите свой логин и нажмите «Показать». Возвращаться в звонок или повторно активировать плагин не нужно. Без `callId` главная страница сразу открывает архив. Локальный адрес: `http://127.0.0.1:18081/?view=archive`. Необязательный `participantId` в ссылке предварительно заполняет поле логина, например `?view=archive&participantId=test1`. Поиск запускается после подтверждения кнопкой или Enter; логин сохраняется при переключении вкладок в текущем окне плагина.

Появятся звонки, в сохранённой истории которых есть указанный `participantId`. У каждого звонка показаны дата начала учёта, время завершения, количество участников и состояние отслеживания. Можно выбрать период по дате начала учёта и скачать полный отчёт звонка в PDF или CSV. Даты фильтра и отчёта используют часовой пояс браузера. Повторные активации одного `callId` объединяются в одну запись; разные звонки в одной комнате остаются отдельными записями. Текущие звонки тоже доступны — их отчёт содержит данные на момент выгрузки.

Архив работает полностью внутри плагина, без запросов к API Meet. У зарегистрированного участника `participantId` совпадает с логином; регистр символов учитывается. Это поиск по заявленному идентификатору, без проверки пароля или сессии: чужой логин можно подставить. Разделения прав между участниками нет. Архивная выгрузка проверяет наличие указанного идентификатора в сохранённых посещениях; прежняя выгрузка по `callId` остаётся доступной по прежнему контракту.

В архив попадают только участники, которых плагин наблюдал через начальный состав и события StreamAPI. Для гостей отдельного восстановления доступа нет: их посещения остаются в общем отчёте, но временный идентификатор не обеспечивает доступ к личному архиву при следующем входе. Для постоянного архива используйте зарегистрированный аккаунт.

История завершённых попыток хранится 30 дней по умолчанию. Истёкшая попытка исключается из поиска и проверки участия сразу, даже до очередного удаления файлов. Если для звонка остаются другие попытки, запись может остаться в архиве тех участников, которые присутствуют в этих попытках. Поиск, пагинация и фильтры используют индекс в памяти; при перезапуске индекс восстанавливается из сохранённой истории. Отдельная база данных и миграция файлов не требуются. При ошибке записи звонок остаётся виден с недоступной выгрузкой до восстановления хранилища.

## Как работает активация

1. Клиент запрашивает активацию звонка через `POST /v1/activations` в Plugin Manager.
2. Менеджер получает манифест из Plugin Registry, проверяет `health-url` и доставляет контекст с `activationId`, `activationSecret` и `callId` на `POST /control` плагина.
3. Backend создаёт отдельный SDK-клиент для активации и подписывается на события `participant.joined`, `participant.left`, `call.ended` в StreamAPI. SDK передаёт данные активации для проверки прав.
4. После SDK `onConnected()` плагин отвечает на `/control` кодом 200. По умолчанию ожидание ограничено четырьмя секундами.
5. Страница плагина читает снимки участников через HTTP API. Открытие и закрытие страницы не управляет подпиской.

На один звонок допускается одна одновременно работающая активация attendance. Повтор одинакового control-запроса использует существующую подписку; изменение параметров того же `activationId` возвращает 409. После неудачного запуска тот же запрос может начать новую попытку.

[Подробный контракт `/control`, ответы и ошибки](docs/activation.md).

## Сборка и локальный запуск

Нужны JDK 25 и доступ к GitHub Packages для скачивания SDK. Gradle Wrapper и версия Node.js для сборки интерфейса настроены в проекте; Gradle скачивает Node.js автоматически.

### Доступ к SDK

Добавьте credentials в пользовательский `~/.gradle/gradle.properties` (Windows: `%USERPROFILE%\.gradle\gradle.properties`):

```properties
gpr.user=YOUR_GITHUB_LOGIN
gpr.key=YOUR_GITHUB_TOKEN
```

Используется GitHub personal access token (classic) с `read:packages` и доступом к пакету SDK. Credentials хранятся вне репозитория. Вместо Gradle properties можно передать `GITHUB_USERNAME` и `GITHUB_TOKEN`; также поддерживаются `GITHUB_ACTOR` и `GH_TOKEN`.

Версия SDK закреплена в [каталоге зависимостей](backend/gradle/libs.versions.toml). Исходники SDK для сборки не требуются.

### Запуск приложения

Из корня репозитория `plugins`:

```bash
cd plugin-attendance/backend
./gradlew build
java -jar build/libs/plugin-attendance.jar --spring.profiles.active=local
```

В PowerShell вместо `./gradlew` используйте `.\gradlew.bat`. Команды запуска выполняются из `backend`, чтобы Spring Boot нашёл внешний профиль `config/application-local.yml`.

`build` выполняет тесты, собирает интерфейс и создаёт `backend/build/libs/plugin-attendance.jar`. Вместо запуска JAR можно использовать:

```bash
./gradlew bootRun --args='--spring.profiles.active=local'
```

Локально backend и интерфейс доступны на `http://127.0.0.1:18081`. Проверка запуска (в PowerShell используйте `curl.exe`):

```bash
curl --fail-with-body http://127.0.0.1:18081/actuator/health
curl --fail-with-body http://127.0.0.1:18081/api/info
```

Healthcheck подтверждает работу приложения. Подписка на звонок появляется после команды активации; до неё запрос состава возвращает 404.

### Разработка интерфейса

Для отдельного запуска Vite нужен установленный Node.js 24. В другом терминале из каталога `plugin-attendance`:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173/?callId=RM_REAL_CALL_ID`. Vite проксирует `/api` на локальный backend `127.0.0.1:18081`; backend запускается с профилем `local`.

## Профили и настройки

Общие параметры находятся в [application.yml](backend/src/main/resources/application.yml). Профиль выбирается явно через `--spring.profiles.active` или `SPRING_PROFILES_ACTIVE`.

| Профиль | Файл | HTTP | StreamAPI | TLS |
|---|---|---|---|---|
| `local` | [config/application-local.yml](backend/config/application-local.yml) | `127.0.0.1:18081` | `calls.vareonix.cc:443` | Да |
| `prod` | [application-prod.yml](backend/src/main/resources/application-prod.yml) | `0.0.0.0:8081` | `nginx:19090` | Нет, внутренняя Docker-сеть |
| `stage` | [application-stage.yml](backend/src/main/resources/application-stage.yml) | `0.0.0.0:8081` | `nginx-stage:19090` | Нет, внутренняя Docker-сеть |

Локальный профиль находится вне ресурсов и не попадает в JAR или Docker-образ. Серверные профили рассчитаны на Docker-сеть соответствующего окружения. Deployer задаёт `SPRING_PROFILES_ACTIVE=prod` или `stage` при запуске контейнера.

| Параметр | Значение по умолчанию | Назначение |
|---|---|---|
| `attendance.activation.start-timeout` | `4s` | Ожидание подключения при активации; должно быть короче HTTP-таймаута Plugin Manager |
| `attendance.streamapi.target` | Из профиля | Адрес gRPC StreamAPI |
| `attendance.streamapi.plaintext` | Из профиля | Подключение без TLS |
| `attendance.streamapi.metadata` | Пустая map | Дополнительные gRPC-заголовки |
| `attendance.tracking.max-calls` | `100` | Максимальное число хранимых трекеров |
| `attendance.tracking.failed-retention` | `1m` | Хранение завершённых и отказавших трекеров |
| `attendance.tracking.cleanup-interval` | `30s` | Период очистки трекеров |
| `attendance.tracking.ignored-participant-prefixes` | `streamapi-`, `EG_` | Служебные участники, исключаемые из учёта |
| `attendance.reports.directory` | `data/attendance` | Каталог долговременного хранения истории, относительно рабочего каталога процесса |
| `attendance.reports.retention` | `30d` | Срок хранения завершённых попыток отслеживания; `0s` отключает автоматическое удаление |

`activationId` и `activationSecret` поступают в control-сообщении от Plugin Manager. SDK использует их для авторизации подписки; глобальный ключ менеджера плагину не нужен.

## Проверка на звонке

### Через серверный Plugin Manager

Для серверного экземпляра сначала разверните сборку плагина `1.0.2` и зарегистрируйте [манифест версии 1.0.2](manifests/plugin-attendance-1.0.2-manifest-1.1.json) в Plugin Registry. Манифест использует серверные адреса `https://calls.vareonix.cc/apps/plugin-attendance/` и запрашивает начальный состав через `initial-state: ["participants"]`.

Создайте звонок, получите его `callId` и отправьте запрос (пример для Bash):

```bash
curl --fail-with-body --request POST 'https://calls.vareonix.cc/v1/activations' \
  --header 'Content-Type: application/json' \
  --data '{
    "callId": "RM_REAL_CALL_ID",
    "pluginId": "attendance",
    "pluginVersion": "1.0.2",
    "pluginRegistryId": "local",
    "requestedBy": "manual",
    "idempotencyKey": "REPLACE_WITH_UNIQUE_KEY"
  }'
```

`callId` — SID комнаты LiveKit вида `RM_...`. Для новой активации задавайте новый `idempotencyKey`; повтор того же запроса с прежним ключом возвращает прежний `activationId`.

По возвращённому ID проверьте состояние менеджера и состав звонка:

```bash
curl --fail-with-body https://calls.vareonix.cc/v1/activations/ACTIVATION_ID
curl --fail-with-body https://calls.vareonix.cc/apps/plugin-attendance/api/calls/RM_REAL_CALL_ID/participants
```

Ожидаются `ACTIVE` у Plugin Manager и `TRACKING` в API плагина. Менеджер доставляет секрет непосредственно backend плагина; вручную придумывать его не нужно.

Откройте страницу:

```text
https://calls.vareonix.cc/apps/plugin-attendance/?callId=RM_REAL_CALL_ID
```

Затем выполните вход и выход проверяемого участника: списки `present` и `left` должны обновиться.

### Локальный плагин с серверным StreamAPI

Профиль `local` подключается к серверному StreamAPI по TLS. Для доставки команды от серверного Plugin Manager локальный backend должен быть доступен ему по HTTPS с маршрутами `/actuator/health` и `/control`. Для такого запуска создайте отдельную тестовую версию манифеста с адресом локального экземпляра.

[Инструкция локальной проверки](docs/manual-sdk-tracking.md). Пример прямого вызова `/control` приведён в [контракте активации](docs/activation.md); для него нужны ID и секрет существующей активации из Plugin Manager.

После активации локальная страница доступна по адресу `http://127.0.0.1:18081/?callId=RM_REAL_CALL_ID`. Необязательные параметры `roomId` и `participantId` задают имя комнаты внизу страницы и выделение текущего участника. Подписанный контекст запуска пока не реализован.

## HTTP API и состояния

Пути указаны относительно backend. На сервере к ним добавляется префикс `/apps/plugin-attendance`; NGINX удаляет его перед передачей запроса в приложение.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | Интерфейс плагина: текущий звонок с `callId`, иначе архив; `view=archive` открывает архив явно |
| POST | `/control` | Запуск активации с ожиданием подключения к StreamAPI |
| GET | `/api/info` | Источник событий, адрес StreamAPI и версия приложения |
| GET | `/api/calls/{callId}/participants` | Состояние подписки, участники и перерывы связи |
| GET | `/api/calls/{callId}/report?format=pdf&timezone=Europe%2FMoscow` | Скачать отчёт; `format`: `pdf` или `csv`, часовой пояс IANA (по умолчанию UTC) |
| GET | `/api/archive?participantId=test1&page=1&limit=20&timezone=Europe%2FMoscow` | Найти сохранённые звонки участника; необязательные `from` и `to` — включительные даты начала учёта `YYYY-MM-DD` в заданном часовом поясе |
| GET | `/api/archive/calls/{callId}/report?participantId=test1&format=pdf&timezone=Europe%2FMoscow` | Скачать полный отчёт звонка с проверкой участия заявленного `participantId` |
| GET | `/actuator/health` | Healthcheck приложения |
| GET | `/actuator/info` | Информация о сборке Spring Boot |

Запрос участников читает уже созданный трекер. Для неизвестного звонка возвращается 404. Снимок содержит `present`, `left`, `trackingSince`, `endedAt`, `stoppedAt`, `gaps`, `serverTime` и состояние подписки. `stoppedAt` — время остановки отслеживания; после него интерфейс не увеличивает длительность открытых визитов. При текущем разрыве связи отсчёт ограничен началом разрыва.

HTTP API сохраняет существующую модель доступа по `callId`, без проверки пользователя Meet. Секрет активации используется только для подписки на StreamAPI и не передаётся в браузер.

Ответ архива содержит `participantId`, `serverTime`, `retentionSeconds` (`0` — бессрочно), `page`, `limit`, `total`, `totalPages` и `items`. В записи звонка: `callId`, `activatedAt`, `trackingSince`, `endedAt`, `stoppedAt`, `status`, `participantCount`, `hasGaps`, `expiresAt` (`null` для активной/бессрочной истории), `reportAvailable`. Записи упорядочены от новых к старым по началу учёта (при отсутствии — по времени активации). Страница начинается с 1, размер — от 1 до 100. Пустой результат возвращается с HTTP 200, неверные параметры — 400. Архивная выгрузка возвращает 403, если заявленного участника нет в оставшейся истории звонка, 404 — если истории нет или срок хранения истёк, 503 — если история временно недоступна. Ответы архива не кэшируются.

Состояния подписки:

| Состояние плагина | Значение |
|---|---|
| `CONNECTING` | Первая подписка ещё не установлена |
| `TRACKING` | Подписка активна |
| `RECONNECTING` | Связь потеряна после начала учёта; SDK переподключается |
| `ENDED` | Получено событие завершения звонка |
| `FAILED` | Подписка завершилась ошибкой |

Это состояния трекера плагина. Состояние активации платформы читается отдельно через Plugin Manager.

При первом подключении к StreamAPI участники из `initialContext.participants` попадают в `present`. Их время присутствия отсчитывается с `trackingSince`. Чтобы менеджер передал список, в опубликованном манифесте укажите `initial-state: ["participants"]`. Снимок хранит последнее известное состояние каждого участника.

После разрыва соединения события за перерыв могут быть потеряны; перерывы отражаются в `gaps` и интерфейсе. Подписка закрывается по `call.ended`, окончательной ошибке SDK или при завершении приложения. Завершённые и отказавшие трекеры удаляются по настройкам retention и cleanup. HTTP-команды ручной остановки нет.

Текущее состояние интерфейса хранится в памяти одного процесса. Полная история сохраняется на диск при изменениях и периодически во время отслеживания. Каждая попытка подписки получает отдельный идентификатор: повторная активация не перезаписывает прежнюю историю. В отчёт включаются все сохранённые попытки для данного `callId`.

После перезапуска архив доступен для выгрузки, но подписка автоматически не восстанавливается: менеджер должен повторно доставить команду активации. Прерванная попытка фиксируется на момент последней сохранённой записи; это не считается фактическим выходом участников. Завершённая история хранится 30 дней независимо от короткого срока хранения трекера в памяти. Архив не содержит секретов активации.

При ошибке записи отслеживание останавливается, а выгрузка возвращает HTTP 503 вместо неполного отчёта. Неудавшаяся финальная запись повторяется при очистке или повторной активации; прежний трекер сохраняется до успешной записи. При восстановлении хранилища история предыдущей попытки сохраняется до запуска новой.

Один каталог истории должен обслуживаться одной репликой. При запуске процесс получает эксклюзивную блокировку `.attendance.lock`: второй экземпляр с тем же каталогом завершится с ошибкой до изменения архива. Блокировка освобождается при остановке или завершении процесса; сам файл может оставаться в каталоге.

В Docker каталог `/app/data/attendance` необходимо подключить к постоянному volume; конфигурация deployer содержит volume `reports`. Не удаляйте его при обновлении контейнера. Каталог должен быть доступен на запись пользователю контейнера `1000:1000`.

Для участников начального состава граница учёта отмечена `*`; неизвестный вход — `?`, без выдуманной длительности. Пока звонок продолжается, открытый период заканчивается словом «сейчас», а итог считается на момент формирования. При текущем разрыве связи итог ограничен началом разрыва; при остановке отслеживания неизвестный выход отмечается границей наблюдения со `*`. Если период пересекает завершённый разрыв связи, итог отмечен `≈`: пропущенные события восстановить нельзя, а вычитать разрыв как доказанное отсутствие участника некорректно.

Короткие пояснения появляются под таблицей только при необходимости. Подписи участников совпадают с интерфейсом: гостевые identity преобразуются в читаемые имена, одинаковые имена различаются короткой меткой. При совпадении первых четырёх символов метка расширяется до уникальной. Если имени нет, используется доступный идентификатор. Пересекающиеся интервалы одного участника учитываются в общей длительности один раз. Для периодов в разные даты выводятся даты, а при переходе часового пояса на летнее или зимнее время — UTC-смещения.

Для скачивания внутри Meet iframe должен разрешать `allow-downloads` вместе с `allow-scripts`. Если сервер возвращает отчёт с HTTP 200, но браузер не сохраняет файл и сообщает `Download is disallowed`, проверьте `sandbox` у iframe. Разрешение задаётся в самом Meet: нужно развернуть исправленную сборку Meet и перезагрузить страницу звонка. Одного обновления плагина для изменения разрешений iframe недостаточно.

Поиск в архиве запускается кнопкой «Показать» или клавишей Enter в поле ввода через JavaScript, без отправки HTML-формы. Это позволяет искать внутри существующего sandbox Meet без разрешения `allow-forms`. Если при нажатии кнопки нет запроса к `/api/archive`, а консоль сообщает `Blocked form submission`, обновите сборку интерфейса плагина и перезагрузите страницу звонка.

CSV использует UTF-8 с BOM и разделитель `;`; значения экранируются, потенциальные формулы защищаются от выполнения при открытии в табличном редакторе. PDF содержит встроенный шрифт с кириллицей и автоматически разбивается на страницы.

## Манифесты и выпуск

Шаблон имени: `plugin-{pluginId}-{pluginVersion}-manifest-{manifestVersion}.json`. Версии плагина и схемы берутся из полей `plugin-version` и `manifest-version` внутри JSON.

| Версия плагина | Манифест |
|---|---|
| `1.0.2` | [plugin-attendance-1.0.2-manifest-1.1.json](manifests/plugin-attendance-1.0.2-manifest-1.1.json) — текущий выпуск |
| `1.0.1` | [plugin-attendance-1.0.1-manifest-1.1.json](manifests/plugin-attendance-1.0.1-manifest-1.1.json) — предыдущий выпуск |
| `0.1.0` | [plugin-attendance-0.1.0-manifest-1.1.json](manifests/plugin-attendance-0.1.0-manifest-1.1.json) — историческая версия |

Содержимое существующих манифестов неизменяемо. Для новой версии создаётся отдельный файл и отдельная запись версии в Plugin Registry.

Версия `1.0.2` включает долговременную историю посещений, минималистичные отчёты PDF/CSV и архив звонков с поиском по логину. Файлы отчётов формируются при скачивании; на диске хранится история в JSON. Существующие файлы истории совместимы с новой версией, миграция не требуется. Перед обновлением сохраните постоянный volume с историей.

[Dockerfile](Dockerfile) упаковывает готовый `backend/build/libs/plugin-attendance.jar`. Для ручной сборки сначала выполните Gradle `build` в `backend`, затем `make image-build` в `plugin-attendance` (нужны Docker и Make). Профиль выбирается при запуске контейнера.

[Workflow plugin-attendance](../.github/workflows/plugin-attendance.yml) на каждой ветке собирает и тестирует JAR. После push в `main` он также публикует образ `ghcr.io/dwspurpleteam/attendance:<commit SHA>` и отправляет событие в deployer. Workflow `images` в deployer создаёт PR с новым тегом образа.

В CI Gradle использует `GITHUB_ACTOR` и `GITHUB_TOKEN`; репозиторию `plugins` нужен доступ к Maven-пакету SDK. Для отправки события в deployer общему workflow требуется секрет `DEPLOYER_TOKEN`.

Изменения deployer сначала объединяются с `dev`, после проверки — с `main` для выкладки в prod. Профиль `stage` подготовлен, но включение stage-сервиса управляется отдельно в deployer. При первом переходе на серверные профили сначала обновляется образ плагина, затем параметры его запуска. [Порядок обновления и серверная проверка](https://github.com/dwspurpleteam/deployer/blob/dev/docs/attendance-deployment.md).

## Тесты и структура проекта

Из `backend`:

```bash
./gradlew test
```

Тесты проверяют обработку участников, повторы активации, ошибки и таймауты `/control`, работу SDK с тестовым gRPC-сервером и загрузку профилей. Для отчётов проверяются история повторных посещений, восстановление архива после перезапуска, блокировка второго процесса, срок хранения и ошибки диска, группировка периодов по участникам и расчёт общей длительности, CSV и многостраничный PDF с кириллицей. Для архива проверяются точное совпадение логина, объединение активаций, фильтры по локальной дате, пагинация, исключение истёкших посещений и HTTP-выгрузка с проверкой участия. Тестовые источники событий и контроллеры находятся только в `src/test`. Отчёт: `backend/build/reports/tests/test/index.html`.

Из `frontend` можно запустить `npm test`: встроенный runner Node.js проверяет таймауты, отмену запросов, корректность скачиваемых файлов и подписи участников. Дополнительные тестовые npm-зависимости не нужны. Gradle `build` и `check` также запускают эти проверки через задачу `frontendTest`.

```text
backend/
  config/                       Внешний профиль local
  src/main/java/ru/itmo/plugins/attendance/
    PluginAttendanceApplication.java
    web/                        HTTP-контроллеры и ошибки API
    configuration/              Spring-конфигурация и свойства
    service/
      activation/               Контракт и данные активации
      events/                   Интерфейс источника и типы событий
      streamapi/                Адаптер Java SDK
      tracking/                 Состояние звонка, история посещений и её хранение
      report/                   Расчёт итогов, подписи, таблица и отдельная PDF-вёрстка
  src/main/resources/           Общие настройки и профили prod/stage
  src/test/                     Тесты и gRPC fixtures
frontend/                       React/TypeScript-интерфейс
manifests/                      Манифесты версий плагина
```

Java SDK используется в `service.streamapi`; трекеры работают через интерфейс `EventSource`. Точка входа приложения — `PluginAttendanceApplication`.
